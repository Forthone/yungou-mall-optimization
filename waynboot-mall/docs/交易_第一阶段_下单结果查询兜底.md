# 普通下单结果查询兜底

## 背景与范围

旧接口只读取 60 秒的 Redis 结果，缓存缺失返回下单错误；前端把查询成功当作创建成功，最多等待约 1.8 秒。本次只调整普通订单创建结果查询，不修改秒杀、支付、库存和消息投递实现，无数据库迁移。

## 链路与判断依据

同步主链路：用户提交 → 短期防重复 key → 本地消息表（ORDER_SUBMIT）→ 返回订单号。异步链路：Relay → RabbitMQ → 消费者 HTTP 回调 → 事务创建订单和延迟消息 → 写短期结果缓存。业务事务提交和缓存写入之间存在故障窗口。

查询为只读操作，无新事务、无重试投递、无库存副作用，不将 Redis 值当作数据库事实，也不回填旧结果覆盖并发更新。

1. 从认证上下文取得 userId，按 userId + orderSn 查询订单。存在即 SUCCESS，返回数据库 actualPrice；该状态只表示创建成功，不表示已支付。
2. 无订单时按 ORDER_SUBMIT + ORDER + bizId 查询 Outbox，解析持久载荷的 order.userId 核对归属。不存在、不属于本人、损坏载荷均返回相同 UNKNOWN，不读取全局结果缓存。
3. 本人消息处于 INIT/SENT 且没有错误提示时返回 PROCESSING。Redis 不可用时仍依据持久消息判断。
4. 缓存错误文本、投递 FAILED 及无法确认的记录返回 UNKNOWN。投递状态和回调一次失败不能证明业务最终失败，当前不提供 FAILED 业务终态。

已有防重复 key 和消息 messageKey 不变。本次不改变事务边界、库存不变量、消费幂等或补偿机制。恢复仍使用原有 Outbox 重试/人工补偿流程，查询接口不触发补偿。

## 接口兼容性与前端

GET /order/searchResult/{orderSn} 路径不变，响应从空成功/业务错误改为 code=200，data 包含 status、message、actualPrice。后端和商城前端需一起更新；旧前端不能直接使用新接口。其他客户端需要同步适配。

前端每秒查询一次，最多 30 次；PROCESSING 继续，SUCCESS 使用数据库金额进入支付页，UNKNOWN 停止并提示稍后查看我的订单。网络异常和等待上限都转为 UNKNOWN，不自动重新下单。轮询期间禁用重复提交，离开页面取消后续轮询和旧结果跳转。

## 验证与运维检查点

- 单元测试覆盖数据库成功优先、SQL 用户条件、缓存丢失/异常、本人消息、外账号/缺失同响应、损坏消息、错误缓存及投递失败、认证用户传递。
- Node 测试覆盖处理中转成功、零元金额、未知停止、网络异常/等待上限、取消。
- 人工验收：仅在本地测试数据上创建本人订单，清理该订单结果缓存后查询应 SUCCESS；另一测试账号查询同订单应 UNKNOWN；暂停消费者后提交应 PROCESSING；恢复后最终 SUCCESS。
- 排查时按订单号关联订单、local_message 的 topic/bizId/status 和消费者日志；不能用 Outbox SENT 判断业务成功，也不能用 RabbitMQ 队列为空判断从未发消息。

## 非目标与后续

本阶段不新增业务失败终态表，不把投递失败映射为最终下单失败；后续如需可靠 FAILED，应设计持久受理状态及消费重试终态。消息 Confirm/Return 闭环、价格快照及其他订单接口归属校验另行处理。
